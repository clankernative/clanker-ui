# Clanker Native UI — agent field guide

Clanker Native UI is a provisional **agent-first component catalog and build-time assembly system**. It is not a runtime UI framework. An agent discovers a component, reads its manifest and fixtures, chooses typed options, and declares it in an app template. The Native build expands the declaration from a locked local package, stages admitted HTML/CSS, and leaves the app in charge of its domain behavior. The browser does not fetch package source or run the catalog CLI.

## Where things live

- `crates/catalog-core/`: package and component metadata, lock validation, discovery, dependency resolution, and typed component contracts. Keep this independent of app I/O.
- `crates/clanker-ui/`: discovery CLI plus `expand` (symbolic templates, bindings and locked resources) and script-free fake-scene `render`. The old `build`/`compose` commands are **not** the app integration path.
- `crates/catalog-core/src/expansion/`: pure declaration expansion and composition. `crates/clanker-ui-runtime/` implements preview-side generic binding ABI 2; Platform implements that ABI independently. Both must pass the identical vectors in `tests/protocol/ui-binding-abi-v2.json`; Platform never vendors or imports the component runtime. See `docs/ui-binding-abi-v2.md`.
- `packages/vanilla/ui-package.json`: package identity, theme, and declared shared resources. `packages/vanilla/components/<name>/component.json` opts a component into discovery; absent metadata means it is not available. `icons.json` is the shared closed SVG geometry catalog; `icon-catalog.json` provides validated human-readable labels and categories for the same names.
- `packages/vanilla/components/<name>/`: component manifest, fragment/template, CSS, and self-authored fixtures. The app owns token overrides; don't edit package defaults to theme one app.
- `examples/`: small local package/CLI proof. `README.md` describes the architecture and its current limitations.
- Platform's `crates/xtask/src/ui_assembly/port.rs` and control-plane build adapter are separate provider-neutral host ports. They capture locked inputs, invoke an independently approved compiler, verify outputs, and stage ordinary templates/resources before normal admission. No component vocabulary or runtime dependency belongs in Platform. Local operator setup uses `DAY2_UI_PROVIDER_PIN_JSON`; the app lock alone never authorizes executable bytes.
- `../clanker-ui-gallery/`: the standalone Native project/task consumer and current Studio target. It is the designated showcase for all fifty-four contracts. Its Native explorer and separate, explicitly labeled component/adapter demonstrations must distinguish host admission from component completeness. Its README documents startup, the bounded workspace, and rejected-submission recovery. Keep screenshot evidence outside both app and package source trees. Use temporary capture directories and viewable PR attachments or immutable review links; do not commit screenshots to this repository.
- Studio's Native project integration consumes the same canonical `ui/ui.lock.json` and an explicitly reviewed executable configuration. Preserve source revision/undo guards, exact local-session binding and honest contract freshness. Static fake-data preview is not admission or a real app. Machine-local project profiles and private source history are not portable dependencies.
- GoLinks is a first consumer of the canonical lock and generic assembly protocol. Its `FRONTEND.md` records component adoption, preserved business/UI boundaries and remaining gates. A sibling package path is an explicit local override, not cold CI provisioning; normal setup must use captured installed inputs.
- `../../internal-tools-toolframe/src/components/`: F# reference contracts, component manifests, fixtures, styles, and tests. **Read but do not copy F# constructors or Scriban templates into this Rust/HTML target.** Port semantics, accessibility, visual tokens, and tested behavior to a Native contract.

## How to use a component

1. Run `cargo run --locked --offline -- find <term> --lock examples/button-app/ui.lock.json` and `describe <name>`; inspect its `component.json`, fixtures, and `graph <name>` before selecting it. Search is literal, not semantic. The canonical Native lock is app-owned `ui/ui.lock.json` (`schemaVersion: 1`, `provider: "clanker-ui.native"`, `package: {name, version, path, digest, inputs}`). All discovery, validation, expansion and render commands consume this same JSON schema; flat and Markdown locks are rejected. `lock` and `native-lock` author identical locks and require `--update` to refresh changed bytes. Inputs are the complete declared package closure, sorted by path, with per-file SHA-256 digests and byte counts. The package digest is SHA-256 over each `path + NUL + decimal bytes + NUL + digest + LF`, not a raw-file concatenation hash. The local example keeps its lock at `examples/button-app/ui.lock.json` so the package path remains relative to the lock directory.
2. The package declares fifty-four component-complete contracts, covering all Toolframe components. Nine retain `integration.native.status: adapter-required`; component readiness does not grant host admission. The twelve composition layouts accept only host-admitted child slots: card requires `body` with optional `actions`; split requires ordered `start` and `end`; cover requires `primary` with optional `top`/`bottom`; layer requires `base`/`foreground`; pane requires `body` with optional `header`/`footer`; sidebar requires `main`/`aside` and orders them by `side`. Container, Stack, Cluster, Grid, Reel, and Switch take implicit body children or an explicit `body` slot. Reel also requires a nonblank accessible label. Pane's bounded heights scroll by default; content height does not. An explicit boolean overrides scrolling independently of height. `collapse-at="never"` means immediate expanded layout, not permanently stacked content. In templates, named children use `<cui-slot name="actions">…</cui-slot>` (and the documented slot name), not raw HTML option strings. Button defaults to `secondary`; layout option names and allowed values come from each manifest and the typed `catalog-core::layout` config. Grid does not provide masonry. Checked page-field bindings and runtime guards remain host capabilities and must not be inferred from this package's CLI fixtures. Avatar optionally accepts a credential-free HTTPS `imageSource` or a host-owned `/assets/app/` or `/assets/instance/` path; the app owns image provenance and acquisition. Activity Feed, Tabs, Segmented Control and Progress Steps support whole named `routes.…()` calls inside Native JSON hrefs, never arbitrary field-bound URLs; route/type/provenance checks remain host-owned. Disclosure uses native `details`/`summary`, and Tabs is link navigation, not a client-side tablist. A component must not create a command or own a route.
3. Keep app-specific `--cui-*` overrides in `ui/clanker-theme.css`. The host must validate and stage the package's styles and app overrides; do not paste generated HTML/CSS into the app.
4. Update the app lock explicitly when any declared package byte changes; a local package edit alone does **not** trigger an app rebuild. Check the output HTML, keyboard behavior, accessibility semantics, responsive layout, and no-JS behavior in a real host build.

## Porting one component well

1. Read Toolframe's `component.yaml`, contract, tests, styles, fixtures, and dependencies. Choose a dependency-first, bounded slice. A Toolframe `experimental` manifest is evidence of a design, not a production readiness claim.
2. Write a target-specific manifest with accurate agent `useWhen`/`avoidWhen`, assets, tokens, invariants, and fixtures. `ready` means component-complete: real rendering, interaction, accessibility, cleanup, and tested adapter ports. It does not grant Native host admission. Record missing host wiring separately in `integration.native` and declare locked port type contracts in `assets.contracts`; a simulator must be explicitly labeled and implement the same contract as a real adapter. Unregistered directories stay invisible. Preserve the closed icon names and the difference between decorative and labeled icons.
3. Implement typed validation and escaping, deterministic rendering, and tests for valid variants/states and invalid input. Reject unknown props, invalid names, unsafe markup/URLs, malformed declarations, and inaccessible states rather than silently changing intent. Keep component CSS and fixtures beside the manifest.
4. Implement declaration rendering, composition, symbolic bindings, resource selection and helper semantics in Clanker UI. Extend the thin Native port only for host-owned admission/staging. Preserve lock/path/digest checks, budgets, Roc-context checks and normal template/form/resource admission. Do not duplicate renderer rules in the platform or introduce runtime package lookups, arbitrary JS, or a second app-operation catalog.
5. Prove the component with real browser behavior and explicit test adapters before marking it ready. Prove the host separately before claiming Native integration: an unwired backend is not a component placeholder, but missing component behavior, accessibility, or lifecycle proof still blocks completeness. Keep `integration.native.status` as `adapter-required` until a real host build and browser review establish the advertised host scope.

## Ownership and demo rules

- Read each manifest's ownership invariants and typed Rust instance before binding data. Configuration is not browser-local state. App/server task data is not a component signal.
- Component status and Native support are separate. Inspect `integration.native` and the host's supported declarations before using a complete contract in a Native template; `adapter-required` components must not be treated as admitted. The currently supported forty-five package contracts expand at build time and declare no component-owned Datastar signals. Copy Field, Theme Switcher, Tooltip, and Toast have host-staged browser installers with exact-root cleanup; their Native readiness is limited to literal static-page declarations, not runtime bindings or live-region replacement. Verify the current Native host adapter's supported declarations separately; package CLI verification does not prove host admission or browser behavior. Form Field uses the browser's draft and the host's existing command transport.
- Keep editable forms out of `data-live` data regions; success may replace the submitted form, while rejection must preserve its draft. Stable IDs must also reserve the derived `-hint`/`-error` IDs and Copy Field's `-status` ID.
- Treat the local GoLinks `/ui-demo` page as sample material only unless the current locked package has been rebuilt and its rendered output and browser behavior independently checked. A host build and browser review are required before claiming integration. Do not paste generated HTML or package CSS into the app.
- A numeric Progress binding needs runtime range validation before admission. A removal Tag is navigation, not a dismissal command. Alert announcements must be explicit. Avatar initials remain literal (one-to-three Unicode graphemes); optional images require a safe HTTPS URL or host-owned asset path, with provenance owned by the app. Page Header has a fixed h1 and optional named admitted actions child. Skeleton is decorative; the app owns loading text and aria-busy. Metric direction and favorability are independent; its announcement text is not a live region.

## Local checks and cautions

- In this repo: `cargo fmt --all --check`, `cargo test --locked --offline`, and `cargo run --locked --offline -- verify --lock examples/button-app/ui.lock.json` (refresh the example lock after declared package changes). `.github/workflows/ci.yml` runs the corresponding portable checks on PRs.
- In a Platform checkout: run scoped `cargo test --locked -p xtask ui_assembly`, `cargo run --locked -p xtask -- verify-fast`, and supported native app builds. Run the frozen-source full `xtask verify` before claiming complete Platform verification. A Linux Rust suite is not macOS isolated-builder or Studio GUI qualification.
- For GoLinks: refresh its lock only when declared package bytes change. Rebuild through Platform with a reviewed compiler pin; inspect admitted forms, drafts, stable live regions, authorization, cursor paging, responsive/accessibility and no-JS behavior. Static rendering does not prove these host/browser gates.
- Early-access release candidates keep CLI 0.1.0 / vanilla 0.7.0, canonical locks, assembly protocol 2 / ABI 2. Follow `docs/INSTALL.md` for reviewed first installation without a source checkout. Project MIT is approved; third-party/font terms remain separate (`LICENSE`, `NOTICES.txt`, `docs/RELEASE-NOTICES.md`). Bundle-level `legal/LICENSE` and `legal/NOTICES.txt` are mandatory verified manifest inputs, outside the unchanged catalog; redistribute the adjacent target-specific notices with a standalone CLI. Re-review notices when dependencies or producer toolchains change. Publication/public-surface and hosted-acquisition proof remain coordinator-owned.
- Release setup is explicit operator work: `native-release` prepares deterministic versioned archives, exact-snapshot standalone CLI and notices assets, their checksums and target-specific `clanker-ui-release-<version>-<target>.json`; `install-native-bundle`/`restore-native-bundle` verify local or exact-version hosted bytes, extract with budgets, and publish atomically to fresh output. They never execute the installed compiler. Archive SHA identifies bytes, not authenticated provenance or execution approval. Do not select latest, overwrite installations or download during compilation. No release publication or CI vendor selection is implied.
- Keep dev/test compiler artifacts below the unchanged 64 MiB executable-pin guard through the reviewed Cargo profiles, not relaxed security budgets. macOS assets and live hosted acquisition require their own qualification; Linux/local tests do not establish them.
- Preserve pre-existing changes in sibling worktrees. A green local check does not mean dependency restore is qualified on a cold runner or that native/browser/full gates are complete. Do not add authored automation scripts or publish/push/deploy without authorization.
